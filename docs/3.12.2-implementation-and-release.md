# 一日千录 3.12.2 开发与发布说明

日期：2026-10-21。版本名 3.12.2，构建号 63，包名 `com.example.inch_light`。

## 1. 本次修改的范围

本次在用户确认的 3.12.1 源码基础上实现记录模块的六项修改，并修复导入确认交互。手机曾安装 3.13.0+59，因此构建号没有从旧源码的 54 简单加一，而是逐次递增到 63。版本名按用户指定保持 3.12.2，尚未开始 3.12.3 的性能修改。

### 快捷操作图标

修改 `lib/widgets/journal_format_icon.dart` 中菜单专用的 B 图标：横向比例从 1.4 调到 1.05，纵向比例为 0.85，重新平移居中，并将该图标笔画从 2.7 调到 2.3。仍在公共 24 像素绘图网格内绘制，菜单继续使用相同的 22 像素图标槽。底部格式栏使用的常规 B 图标没有缩小。

### 合集列表

修改 `lib/screens/journal_page.dart` 的合集窗口。列表行取消自身水平内边距，直接使用窗口内容区的左边缘，从而与标题对齐；启用紧凑行密度并调整垂直内边距。保留名称、数量、选择与滑动删除行为。自动化检查实际几何位置和行高，手机上也打开了真实合集列表。

### 标点管理

实现位于 `lib/utils/journal_operations.dart`。先将 Quill Delta 拆成保留属性的逻辑行和字符，再逐行处理；使用 Unicode rune 边界，避免拆坏辅助平面汉字和 emoji。处理后通过 Delta 重组，保留段落类型及加粗、斜体等富文本属性。

末尾检查分为三步：

1. 段首是引号且该段始终没有对应闭引号时，在段末补齐闭引号。
2. 从末尾剥离待检查的外层句号，沿连续闭合引号、括号向内检查。如果闭合符号内已有句末符号，则删除多余外层句号，不再新增。
3. 向前匹配闭合符号对应的开符号，处理同类嵌套；如果开符号前已经是句号、问号、叹号、省略号等句末符号，该段末尾同样不新增外层句号。

例如：

| 输入 | 处理结果 |
| --- | --- |
| `开始时间。（说明）。` | `开始时间。（说明）` |
| `开始时间。（说明）` | 保持原样 |
| `开始时间？（说明）。` | `开始时间？（说明）` |
| `正文（“内容。”）。` | `正文（“内容。”）` |
| `前句。后句（说明）` | `前句。后句（说明）。` |

最后一例保留了当前句需要的句号：不会只要前文出现过句号，就误判整个段落已经结束。中英文句末符号、嵌套闭合、连续重复执行、尾部空白及跨富文本片段都加入了回归用例。

行内代码字符视为不可改写内容。段首清理不会进入代码，末尾代码也不会被自动加句号；代码块整行跳过标点管理。匹配括号时忽略代码内部的符号，避免把代码中的括号当作正文结构。

## 2. 导入问题如何定位与处理

两条入口共用 `AppProvider.importData`，数据先完整解析，再更新各业务区。验证使用了用户提供备份中的纯 JSON 内容；Markdown 围栏只是原文件的存放方式，最终版本没有加入 Markdown 导入功能。

原交互在读取后将“确认导入”放在设置页卡片底部，在手机上可能位于屏幕外，入口点击后没有清楚可见的下一步。按照用户最终要求，文件与剪贴板读取完成后统一弹出 `AlertDialog`，显示原有覆盖提示与取消／确认按钮；确认后调用导入，取消不修改数据，导入成功显示实际结果。

Android 的 `DataImport.kt` 兼容两种文件选择返回方式：优先读取 `Intent.data`，必要时读取仅包含一个项目的 `ClipData`。明确请求单文件选择，并向文档提供方传入既有备份目录；是否采用初始目录由系统文件选择器决定。读取仍使用 UTF-8，清理 BOM；Dart 纯 JSON 解析同时清理首尾空白。

自动化覆盖文件入口、剪贴板入口、弹窗可见性、取消、导入与持久化；真实手机上实际选择本地 JSON 文件和使用剪贴板纯 JSON，均经过确认弹窗并显示“导入成功”。

## 4. 键盘异常的排查

本轮曾出现微信输入法被系统标记为已显示，但实际内容高度接近 0 的状态。通过系统输入法状态、窗口 content inset 与实际截图确认，随后临时切换到已安装输入法、重启微信输入法进程并恢复原选择。未清除数据、未修改应用代码或全局键盘设置；搜索和正文编辑界面都重新显示了完整键盘。

后续真机验证不再使用 `adb shell input text` 或硬件文字注入。标点专项通过调试连接直接调用手机应用中的实现验证，不改写用户笔记。

## 5. 验证与构建方法

项目使用现有 Flutter 工具链与锁定依赖。当前电脑需显式设置 Android SDK 与 Gradle 缓存位置，依赖来源与原锁文件一致。验证命令为：

```powershell
dart format --output=none --set-exit-if-changed lib test
flutter analyze --no-pub
flutter test --no-pub
flutter build apk --debug --split-per-abi --no-pub
flutter build apk --release --split-per-abi --no-pub
```

`--no-pub` 使用已经按锁文件解析好的本机依赖，避免无关依赖升级。构建前核对 `pubspec.lock` 未被意外更新。发布使用三架构 split APK，版本名均为 3.12.2，实际 versionCode 分别为 armeabi-v7a 1063、arm64-v8a 2063、x86_64 4063。

格式、静态分析与全量 147 项测试通过；手机进程内另行执行 7 项标点专项验证，包括用户两条例句及句末符号场景，全部通过。静态与自动化通过不替代安装验证：每个拟安装包先核对包名、版本与签名，再安装、启动并读取已安装版本，最终拉取已安装 APK 比较 SHA-256。

## 6. 私人备份如何从发布历史排除

本地两个中间提交包含私人备份，远程主分支仍停留在干净的 3.12.1 版本。因此没有直接推送本地 `main`。保留原目录、本地提交及备份，从远程 `origin/main` 创建独立工作树，复制最终源码、测试和文档，明确排除私人备份、签名文件、缓存、构建目录与临时截图。

发布提交由远程现有主分支直接推进，采用普通快进 Push；不覆盖已有标签、不强推、不重写用户的本地备份历史。工作树中的最终源码应与本机构建源码相同，并核对复制后的文件清单与差异。

## 7. GitHub 发布步骤

1. 在用户明确授权后，将 D 盘本次日志同步到项目 CHANGELOG，并更新 README、帮助与验证记录。
2. 完成正式三架构构建、版本及签名检查，正式 ARM64 包保留数据覆盖安装、启动与哈希核验。
3. 复核干净工作树中的待提交文件，创建描述具体改动的 Conventional Commit，普通 Push 到远程主分支。
4. 创建 `v3.12.2` 标签并推送。创建正式 GitHub Release，说明与本次 CHANGELOG 一致，上传三架构正式 APK。
5. 使用 GitHub API 核验标签目标、Release 状态、说明与资产；重新下载资产比较 SHA-256，并与本地正式包和手机已安装 ARM64 包对应。
6. 检查主分支及标签的 GitHub Actions，记录实际结果。若尚未完成，明确记录待验证，不把运行中写成通过。

GitHub 身份验证使用当前电脑 Git Credential Manager 中已有的授权；凭据仅在进程内使用，不写入文档、脚本参数或源码。API 请求沿用本机 Git 已配置的网络代理。插件没有提供 Release 及二进制上传接口，所以这些操作通过 GitHub API 完成。
